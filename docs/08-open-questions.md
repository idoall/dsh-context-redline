## Q6 · 子会话用"一次性"还是"可续接"？——**`✅ 已定`：可续接（推荐 B，用户 2026-09-30 拍板）**（**推荐已按实测更正**，阻塞 M5）

**背景（新核实的事实，见 `docs/01` F12.1/F13.2）**：两种形态的**回传行为不同**——
一次性子会话的结果只回到**调用方**（由我们插件发起时，**父会话不会被唤醒**）；
可续接子会话在 settle 时由**运行时**往父会话追加 `subagent-settled` 结算通知 → **父会话会自动继续**，
而且它在父会话活着时还能在官方 UI 里**直接续聊**、有独立 **Stop**。
另经实测：**fork provider 实现了 `prepareContinuable`** ⟹ "用编辑过的上下文做种子"和"可续接"**可以同时拿到**。

| 选项 | 说明 | 代价 |
|---|---|---|
| A. 一次性（`start('fork', …)`） | 结果回到我们，父会话不自动继续；子会话是终态、只读 | 要"主会话接着干"就得我们替它说话，或让人手工转达 |
| **B. 可续接**（`startContinuable({provider:'fork'})`）**← 推荐** | 平台自带返回指引 + 结算通知 + 续聊 + Stop；父会话据此继续 | 生命周期由平台的 continuation manager 管；**共享进程内名额**（`maxActiveSubagents` 默认 8） |

**推荐 B**，理由：你的原话就是"**子会话完成时，主会话根据子会话结果继续后面的任务**"——
只有 B 让这条链路成为**平台行为**而不是我们自造的约定；A 只在"我只要一个结果、自己处理"时才合适。
**影响面**：`docs/06` §3.1（已按 B 写）、`docs/02`（L2 / 数据流 / 模块名 / 存储）、`docs/03` R5.1/R5.1.2.1、`docs/04` M5 的产物与 DoD（**M7d 已改为"父不在进程时的冷恢复体验"**，不再把 `startContinuable` 放到后续阶段）。
**若你选 A**：`docs/06` §3.1 与 `docs/03` R5.1 的"结果回流"部分要整段删掉，并在界面上明说"父会话不会自动收到结果"。
**⚠️ 前置**：这条主线的端到端行为**未真机验证**（`docs/01` V10/V11）——`docs/05` §4 已把它们列进 `#19/#23` 的前置；
未通过前**不许**在界面/文档里宣称"父会话会自动继续"。

## Q11 · "能回滚"要不要进 v1？——**`✅ 已定`：A 完整回滚**（用户 2026-09-30 拍板；**仅当 V8 未通过时**才自动降级为 A′ 本地台账）

### Q11.0 先说清"**能回滚**"到底指什么（用户 2026-09-30 问）

**场景**：你在右侧把第 200 轮的一条**用户消息**改了，并点了「应用到会话」。过一会儿发现改错了 —— 模型看到的是错的内容。

**回滚 = 把"模型看到的内容"恢复成你选的那一版**：

1. 那一条上打开「**版本历史**」→ 看到 `#A 原始` → `#M 第 1 次改写` → `#K 回滚`；
2. 选 `#A` → 点「恢复这一版」→ **二次确认**；
3. 我们**再往会话追加一条替换事件**，把当前可见内容变回 `#A` 的正文 → 模型此后看到的就是原文；
4. 行上显示完整关系链 `原 #A → #M → #K → 回滚 #N`，每一步都能展开看正文。

**关键澄清（三条容易被误解的）**：

| 误解 | 事实 |
|---|---|
| "回滚就是把我改错的那条**删掉**" | ❌ **删不掉**（会话日志 append-only）。回滚是**再遮蔽一次**：错误的那版还在日志里，但**模型看不到了**。 |
| "改前的原文需要我们自己额外备份" | ❌ **不需要**。原文一直在日志里（append-only 的天然效果）—— 这正是图 2 ④ 说的"**改前自动归档**"。 |

### Q11.2 用户的反驳与我的更正（2026-09-30）

**用户说**：

## 8.5 用户 2026-10-01 提的替代方案：新建**普通会话**当子会话（`[子会话]` 标题 + 指定模型）——**不采纳**

用户提议：如果不能把子会话缩进嵌到左侧列表，那就**新建一个普通 session**，把上下文交给它，
标题前加 `[子会话]`，指定模型与推理档，执行完再返回父会话。

**为什么不采纳**（`docs/01` F36 / F37）：
1. **丢掉回程通道**：`ctx.subagents.prompt` / `sendMessage` 都要求**直接父子邻接**（direct parent/child adjacency）。
   普通会话不是子会话 ⟹ 它**没有**任何官方通道把结果送回父会话，只能人肉复制粘贴。
2. **没有 fork 种子**：把"已完成的历史"作为子会话起点，是 **subagent 通道**的能力；普通会话只能从空上下文开始。
3. **解决不了它想解决的问题**：用户想要它的动机是"**左侧列表里看得见**"，而官方会话侧边栏**隐藏/省略**
   subagent 来源的会话，也**没有"插入新行"的插槽** —— 新建一个**普通**会话确实能在左侧看得见，
   但它就不再是"子会话"（没有父子关系、没有回流、没有种子），是**两害相权取其更差**。
4. 用户想要的"指定模型 + 上中下推理档"**continuable 子会话就能给**（`agentOptions`），不需要绕路。

**结论**：继续走 **continuable 子会话 + 官方团队**；缺的只有**界面入口**（打开它 / 给它发消息 / 看它状态），
那正是我们的面板职责（R5.1 / R5.1.3 / R5.1.4）。若将来官方为"左侧可见"开出插槽，再评估。
