# 06 · 编排规格：快照 → 子会话 → 压缩 → 指挥

> 对应 M5。**这一步的核心动作全都会写会话或建会话，天然是"用户在场才能验收"的一步。**
> 本文件只写：① 语义边界 ② 每一步的产物与校验 ③ 授权清单 ④ 失败码 ⑤ 明确不做的事。

---

## 1. 先划清边界：快照 + 子会话**只解决一半**

| 问题 | 快照 + 子会话 | 谁解决 |
|---|---|---|
| **上下文膨胀**（历史越滚越大，每轮全量重发） | ✅ 解决（新会话起点干净） | 本文件 |
| **历史污染**（过去累积的错内容进了种子） | ✅ 解决（改过的内容进种子，旧的错内容不带过去） | 本文件 + 编辑面 |
| **未来的注入漂移**（宿主每轮重新注入 `runtime-context` / AGENTS.md / 技能目录） | ❌ **不解决** | **固定块层**（`docs/02` L3） |

**一句话**：**快照切断"过去"，固定块守住"未来"，缺一不可。**

**为什么"守未来"不能省**：子会话是一个**新的 sessionId**，宿主照样每轮往里注入。
你没改注入源，漂移会在新会话里**原样重演**。所以固定块必须做成 **workspace 级**
（子会话才继承得到），并且要在子会话里继续做漂移检查。

## 2. ⚠️ 最容易搞错的一条：种子取自**日志**，草稿不会过去

- fork 的种子 = 父会话 `snapshotEvents()` 里**最后一个 `turn/end`** 之前的全部事件（`docs/01` F10）。
- 我们的**草稿只在本插件数据目录里**（`docs/01` F5 的反面：草稿不是会话事件）。
- **推论 1**：**没点「应用到会话」的改动，一个字都不会进子会话。**
- **推论 2（⚠️ 反过来也成立，且很容易被误判）**：**已经「应用」过的改动（包括你后来发现改错的那次）照样会进子会话** ——
  因为种子是**日志前缀**，"替换事件"本身就在日志里，子会话 fold 之后看到的就是**改后的内容**。
  ⟹ **"开一个新子会话"不能撤销错改**；要撤销，必须在**父会话**里先把它改回去（或从**早于那次改动**的切点分叉，
  而官方 `spawnTeammate` / `startContinuable` 用的是**最新** `turn/end`，我们 v1 也随它 —— 所以"从更早的快照分叉"
  **不是**默认行为，属于将来可加的能力）。

由此得到一条**强制的界面顺序**（`docs/03` R5.2）：

```
有草稿 → 先提交（逐条列出要改什么）
        → （建议）把目标/约束存成 workspace 固定块
        → 冻结
        → 开子会话（人写首条任务）
        → 子会话空闲时压缩
        → **后续的派活 / 任务板 / 成员导航交给官方 Agent Teams**（Q12=A，见 §3.2 与 §7）
```

`plan.next` 就是这条顺序的机器表达（§6）。

## 3. 逐步：产物与"怎么知道成功"

| 步 | 动作 | 产物 | 怎么知道成功 | 写到哪 |
|---|---|---|---|---|
| ① | 编辑（草稿 / 求助的更正 / 固定块） | 见 `docs/02` §5.2 | 界面回执：`未生效` / `原 #N → 新 #M` | 我们的数据目录 |
| ② | **应用到会话** | 会话日志里一条 `surfaceOp:{op:'replace'}` | 重新拉 `readSurface` 能看到替换关系；`edits.list` 有记录 | **会话日志**（append-only） |
| ③ | **冻结快照** | 一条 `FreezeRecord` | `snapshot.list` 里能看到；**会话事件数不变**（关键反证） | 我们的 sqlite |
| ④ | **开子会话** | 一个新的 sessionId | **确认框**（取消 → `child.list` 无新会话；确认 → 新会话存在）→ 子会话能看到父会话的**已完成轮次**；父会话**此后**的轮次**不会**进去 | **新会话**（**可续接**，见 §3.1） |
| ④′ | **压缩前体检**（执行前清单） | 一份"将要发生什么"的清单 | 清单里能逐项看到：目标 `childId`、将被摘要替代的**区间与条目数**、**不可逆**提示 | 只读 |
| ⑤ | **压缩** | 子会话历史被一段摘要取代 | 子会话日志出现 `compaction/*` 事件；`compactNow` 返回结果非 null；界面上显示**实际**范围 | 子会话历史（**不可逆**） |
| ⑥ | **只读地看状态** | 子会话的阶段 / 耗时 / token | 读平台的 `subagentCatalog`（父会话）+ `subagentTiming`（子会话）；**不自建** | 只读 |
| ⑥′ | ~~派活~~ / **不做**（Q12=A） | — | **交给官方 Agent Teams**：要派活/任务板就用官方团队；要继续跟**这个**子会话说话，就在**官方子会话视图**里用它的输入框；要停就按它的 **Stop**（`subagents/interruptByParent`） | — |
| ⑦ | **结果回流**（**平台自动，不是我们造的**） | 父会话日志里出现一条 `subagent-settled` 结算通知（可能还有子会话主动 `sendMessage` 来的 relay 消息） | 父会话被唤醒并继续下一轮；这两类消息在父会话里能看到且**来源可辨** | **父会话日志** |

### 3.1 子会话的两种形态：**v1 选"可续接"**（本轮更正的设计决策）

| 形态 | 调用 | 主会话会被唤醒吗 | 子会话能续聊吗 | v1 |
|---|---|---|---|---|
| 一次性 | `ctx.subagents.start(name, …)` | ❌（除"模型自己用工具发起"那条路径）；结果只回到**调用方** | ❌ 终态、只读 | ❌ |
| **可续接** | **`ctx.subagents.startContinuable({ provider:'fork', parent, prompt, label, signal })`** | **尽力而为**：运行时**在 `send_message` 可用时**自动追加返回指引；settle 时**尝试**往父会话投递 `subagent-settled` 结算通知 | ✅ 持久会话，按顺序收后续消息、可单独 Stop | ✅ **默认** |

**为什么 v1 必须用可续接**：你要的是"**子会话完成时，主会话根据子会话结果继续后面的任务**"。
一次性形态下，若由**我们插件**直接发起，父会话**不会**被唤醒——结果只落到我们手里，于是只剩两条烂路：
要么我们替父会话往会话里塞一条消息，要么让用户手工转达。

**可续接形态下这条链路是平台自带的**（已核实，`docs/01` F12.1 / F13.2）——注意措辞里的"尝试"：

```
人点「开子会话」（人写首条任务）
  → 我们调 startContinuable({provider:'fork'})        ← 种子 = 父会话已完成轮次（含已应用的编辑）
  → 运行时**在相邻 send_message 工具可用时**在首条任务后追加「返回指引」：
      "你的父 agent id 是 X；收工前用 send_message 把结果发给它；
       父会话不会自动收到你的 transcript / 工具输出 / 思考；
       结论影响父会话下一步时就早点发"（发消息不会结束你的回合）
  → 子会话干活（中途可随时 send_message 回流阶段性结论）
  → 子会话 settle → 运行时**尝试**往父会话投递 subagent-settled 通知
      "Background subagent <id> finished and will do no further work unless you send it more."
      + 它的结束语（completed / aborted / max-tokens / refusal / error 各有对应人话）
  → 投递成功 → 父会话按 queue/steer 收到并据此继续；**父 Agent 不在进程 → 不投递**；异常只 warn
```

**我们的配套（四件，第 1 件是"不要做"）**：
1. **不要 import/复刻 `withContinuableReturnGuidance`**——它是运行时内部函数，插件调用者不该碰；
   我们**只传人写的首条任务**。"指引有没有真被加上"由 **V11 真机验**，不靠假设（`docs/01` F12.1 第 1 条）；
2. 确认框里**如实告诉人**"父会话不会自动收到子会话的 transcript / 工具输出 / 思考"（`docs/03` R4.3）；
3. 面板里把**结算通知**与子会话状态显示出来，并把"**已收到结算通知**"与"**父会话下一轮已开始**"分成**两个状态**——
   只有拿到父会话里可关联的后续证据（新的 `turn/start`）才敢说"已继续"（`docs/03` R5.1 第 4 项）；
4. 投递失败/父不在进程是**正常分支**，不是异常：界面给 `回流未确认`，并提供"**让主会话接着做**"的人工入口。

### 3.2 ★ A′：**用官方成员，并接上官方协作层**（Q12 用户已定，依据 `docs/01` F32–F34）

**核心决定**：我们的"开子会话"**优先调官方** `spawnTeammate(context:'fork')` —— 它建出来的是**进 roster 的正式 teammate**，
种子又是**父会话已完成轮次（= 你编辑过的上下文）**。这样"任务板 / 成员导航 / 派活 / 打断 / 实时刷新"**全是官方的**，
我们一行协作逻辑都不用写；只有团队不可用时才退到"裸续接子会话"。

| 我们做什么 | 走官方哪个口 | 我们**不**做什么 |
|---|---|---|
| **建子会话** | **优先**：`ctx.agentTeams.spawnTeammate(lead, { context:'fork', provider:<forkProvider>, name, description, prompt: 人写首条任务, signal })`；**兜底**：`ctx.subagents.startContinuable({provider:'fork', …})`（裸子会话，界面**如实标注**） | 不造"成员"概念、不自己拼种子 |
| **派活**（适配调用官方的） | `ctx.agentTeams.sendMessage(lead, { target: <名册名>, content, signal })`（返回 `accepted/queued`） | 不实现自己的消息/排队/送达 |
| **任务板** | 读 `agentTeam` 投影（客户端）/ `listTasks`（宿主）；写 `createTask` / `updateTask`（**revision 乐观校验**） | 不自己存任务、不自己算依赖就绪 |
| **成员导航** | `listMembers` + 跳官方视图（页头 Agent Teams 面板 / 子会话对话） | 不画成员树、不在左侧列表嵌套 |
| **判断来源** | `tryMembership(agent)` | 不按 label 猜 |
| **打断** | `ctx.agentTeams.interrupt(lead, targetName)`（团队成员）；裸子会话才用 `subagents.interruptByParent` | 不自己发取消信号 |
| **结果回收** | **只做可见性**：读父会话的 `subagent-settled` + 本地"已查看"标记 | 用户明确"回收可以不做"——我们不自动汇总 |
| **只有我们有** | ① 冻结快照记录 ② `snapshot_links`（来自哪条快照） ③ `pending_results`（已查看标记） | — |

**降级（写进实现，不是"以后再说"）**：`ctx.agentTeams` **不存在**（团队未启用）→ 上表"走官方"的所有对接点**消失**
（不是报错、不是空面板），只剩"建裸子会话 + 状态 + 回流可见性"；服务在但**拿不到 live Lead** 时同理。
**⚠️ 能建成员的只有 Lead**：`spawnTeammate`/`interrupt` 要求 caller 是本次会话的 live Lead Agent（`ctx.agents.get(sessionId)`）。

**容量约束（要能操作，不只是提示）**：可续接子会话共享**进程内名额**，`maxActiveSubagents` 默认 **8**，
超出时新建/冷恢复以 **`ACTIVATION_LIMIT_REACHED`** 拒绝（**不排队**；也与"保留但暂停"无关——它就是拒绝）。
界面必须：① 显示 `活跃 N / 8`；② 触顶时给人话（`活跃子会话已达上限 8：等某个结束，或先关掉一个。`）；
③ 明确**名额只在当前进程内**（重开进程后从持久会话冷恢复会重新占名额，冷恢复也可能被拒）；
④ 子会话**结束后名额才释放**（"让它停"才是回收动作，别让人以为不管它就自动释放）。
⚠️ **官方团队的 teammate 也占同一份额度**（`docs/01` F31，本机 `maxMembers` 为 8）——两者相加才是真实占用。

| A7 | `child.compact` | 子会话历史被摘要取代 | ❌ **不可逆** | 压哪个子会话、预计丢什么（原文会被摘要取代） |
| A8 | ~~`child.send`（派活）~~ | **不做**（Q12=A）——派活是官方 Agent Teams 的职责 | — | — |
| A9 | `apply.rollback`（回滚） | 往会话日志追加一条 replace，把模型看到的内容恢复成选定的历史版本 | ❌ append-only；**但回滚本身还可以再回滚**（目标 = 新的替换体） | 哪一条（当前可见 `#seq`）、恢复到哪一版（`#toSeq` 及其正文摘要）、为什么 |
| A10 | `child.interrupt`（打断子会话） | 向子会话发出取消信号 | ❌（已提交的工作不会被回滚） | 目标子会话 id、**当前状态**、发出的信号是什么、"已提交工作不回滚"这句实话 |

**"单独点头"的粒度（避免两种极端）**：以下几类是**本地可逆写入**，只需**一次**确认（且有"放弃"路径），
不必套用 A1–A10 的清单式授权；其余一律按上表逐次列清单：

| 动作 | 为什么可以只一次确认 |
|---|---|
| `draft.update` / `draft.reset`（保存/放弃草稿） | 不写会话、随时可放弃、可重复 |
| `snapshot.create`（冻结） | 只写我们自己的库，可删除 |
| `invariant.save`（存固定块） | 只写我们自己的库，可退休且历史保留 |

> 换句话说：**写会话 / 建会话 / 改变运行中的子会话 / 不可逆** → 清单式授权；
> **只写本地且可逆** → 一次确认 + 明说作用域即可。

**界面义务**：动作旁必须能看出"这一步会**写会话**吗"，文案不许含糊（`docs/03` R3.3 / R4.3）。

## 4.1 「允许创建」确认框（图 4 的体验，**必须是可观察的 UI 条件**）

点「开子会话」后**在面板内**弹出，框内逐项列出（缺一项都算没实现）：

| 项 | 内容 |
|---|---|
| ① 种子范围 | `cutSeq` —— 父会话**最后一个 `turn/end`** 的 seq（"冻结到这里为止"） |
| ② 首条任务 | **人写**，必填（空则不允许确认）；这是子会话的第一条 user 消息 |
| ③ 继承范围 | ✅ 继承：父会话**已完成的对话历史**（含你已应用的编辑）；❌ 不继承：父会话的**工具授权/权限**、父会话此后的新轮次、**以及父会话不会自动收到子会话的 transcript / 工具输出 / 思考**（子会话要靠 `send_message` 主动回传，收工时平台另有结算通知） |
| ④ 副作用 | 新建一个会话；种子是**一次性**的；父会话之后的新轮次**不会**进去；子会话是独立 sessionId（workspace 级固定块对它可见） |
| ⑤ 取消 | **取消 = 什么都不发生**（不建会话、不写日志） |

## 4.2 压缩前必须报什么（"必须丢的如实报"）

| 时点 | 必须显示 |
|---|---|
| 执行**前** | 目标 `childId`；将被摘要替代的**区间（按 surface 顺序）与条目数**；**不可逆**提示（"原文会被摘要取代"） |
| 执行**后** | **实际**被替代的范围与结果（条目数/token）；`compactNow` 返回 null 时要明说"没有可压缩的范围，什么都没改" |
| 失败时 | 失败码 + **人话**（`docs/06` §5）+ "失败尝试通常会留在日志里"这句实话 |

## 5. 失败码 → 人话（`compactNow` 的 `ManualCompactionError`）

| code | 含义 | 界面文案 | 下一步 |
|---|---|---|---|
| `busy` | 子会话不是空闲（有轮次在跑 / 有别的 maintenance / 已有 `compaction/start` 锁 / 轮次未闭合） | `子会话正在运行，等它空闲再压缩。` | 按钮置灰；提供"看状态" |
| `cancelled` | 被取消 | `压缩已取消，会话未被改动。` | 可重试 |
| `changed` | 选中的区间在摘要期间被改动 | `这段时间里会话变了，压缩没有执行。` | 重新体检后重试 |
| `summary` | 摘要请求失败 | `摘要生成失败了，会话没有被压缩。` | 可重试；失败尝试会留在日志里（如实说） |
| `commit` | 提交阶段失败 | `压缩没能写入会话。` | 提示重试；不要重试多遍（会留多条痕迹） |
| `persistence` | 落盘失败 | `压缩写入了但落盘失败。` | 先看日志再决定 |

**其它前置失败**（体检阶段就该拦掉，不该走到执行）：
拿不到子 Agent（`ctx.agents.get` 为 undefined）→ `这个子会话当前不在进程里，压缩需要它活着。`；
`ctx.compaction` 服务不存在（V2 待验证项失败）→ 降级为"引导你在子会话里执行 `/compact`"。

## 6. `plan.next`：把"下一步该做什么"变成机器判定

判定**次序**（纯函数，可单测；每一条都带 `reason` 给界面显示，不允许让用户猜）：

| 序 | 条件 | 返回 | 需要授权 |
|---|---|---|---|
| 1 | 轮次未闭合 | `waitTurn` | ❌ |
| 2 | 有未提交草稿 | `applyDrafts`（理由必须写明"**种子取自会话日志，草稿不会带过去**"） | ✅ |
| 3 | 没有任何固定块 | `pinInvariants`（理由：没有固定块 → 子会话里没人守漂移） | ✅（**建议**级） |
| 4 | 已冻结但未开子会话 | `startChild`（**可续接**，见 §3.1） | ✅ |
| 5 | 子会话存在且空闲、且历史很长 | `compactChild` | ✅ |
| 6 | **有子会话刚 settle、其 `subagent-settled` 通知还没被"处理"** | `reviewChild`（去看结果；由人决定："自己接管"还是"交给官方团队继续"） | ✅ |
| 7 | 都已就绪 | `idle`（**到我为止**：后续派活/协作不归我们，见 §3.2） | ❌ |
| — | 都不适用 | `idle` | ❌ |

**第 6 条的"还没被处理"必须是有定义的，否则它就是一个永远为真的条件**：

| 项 | 定义 |
|---|---|
| **待处理项的键** | `(父会话 id, 父会话日志里那条 `subagent-settled` 通知的 seq)` —— 用日志位置当键，重启后能重算 |
| **"已处理"记在哪** | **我们自己的 sqlite**（`pending_results(parent_session_id, settled_seq, seen_at, note)`）；**不写会话**、不改子会话状态 |
| **什么时候算"已处理"** | 人在面板上点了 `已查看`（或点了 `让主会话接着做`）——**不是**"父会话跑了下一轮"就自动算处理完（那可能只是别人发的一条消息触发的） |
| **重启后怎么恢复** | 从**父会话日志**重扫 `subagent-settled` 通知，与本地 `pending_results` 求差 → 未记录的重新标为"待处理" |
| **读不到**（V10 未通过 / 读失败） | **不显示**"待处理的结果"这一区块（宁可不显示，也不猜）；并提示"平台目录不可用，请用官方页头目录查看" |

**边界**：`orchestration` 这一层**只回答"该做什么"，不做什么**——不写会话、不建会话、不压缩。
执行永远由上层在用户点头之后发起。

## 7. 明确不做（避免范围膨胀）

- ❌ **不自动开子会话**：`child.create` 只在用户点了按钮之后调用。
- ❌ **不自动重注入**：固定块只**报告**漂移；重注入必须人点。
- ❌ **不自动压缩**：压缩不可逆，必须人点（且先过体检）。
- ❌ **不伪造宿主内容**：`runtime-context` / AGENTS.md / 技能目录由宿主生成，我们**造不出**官方快照；我们追加的一律是**带结构化头部的普通 user 消息**。
- ❌ **不做"删除历史"**：append-only 里没有删除；能做的只有遮蔽（模型不可见、日志仍在）与压缩（体积变小但不可逆）。
- ❌ **不批量静默操作**：即使"全部应用"，也要逐条列出 `#seq`。
- ❌ **不自己做协作层**（**Q12=A，用户已定**）：派活（`child.send`）、任务板、成员导航、团队编排**一律不实现**——
  官方 Agent Teams 已有，且两套并存会互相干扰。我们的面板只到"**建子会话 + 状态/回流/来源可见 + 跳转**"为止（§3.2）。
